# CODEX TASK — MAKE PREDATOR ISLE’S NEARBY TERRAIN LOAD ALMOST INSTANTLY

## OBJECTIVE

Optimize the existing C# terrain system so the central 3×3 area becomes visible and safely playable extremely quickly, including on lower-end PCs, while preserving realistic terrain, existing biomes, caves, and large viewing distances.

The project already has nested terrain rings and small nearby patches. Do not create another competing terrain architecture or assume that simply reducing polygon counts will solve the remaining delays.

The intended architecture is:

SHARED TERRAIN DATA
→ independently ready nearby terrain and collision
→ reusable GPU-displaced render grids
→ detailed terrain materials
→ separately streamed cave interiors and supplementary features.

Implement these changes in the actual project. Profile, test, inspect rendered results, and report measured improvements.

## 3. REMOVE UNNECESSARY WHOLE-WORLD PUBLICATION BARRIERS

The central 3×3 must not wait for every distant patch or unrelated underground region.

Refactor publication into independently safe LOCAL transactions.

A local surface group should require only:
- Its terrain data.
- Required collision.
- Valid connections to its currently published neighbors.
- Any cave-mouth or geological geometry that affects that group.

Do not require all requested rings to finish before publishing newly ready nearby terrain during ordinary movement.

Use explicit readiness states such as:

Requested
→ DataReady
→ SurfaceReady
→ CollisionReady
→ Published
→ OptionalDetailReady

Readiness must be versioned by terrain source revision, patch ownership, and boundary dependencies.

A local transaction must retain:
- Exactly one visible owner for each surface region.
- Valid 3:1 transitions.
- No exposed holes.
- No conflicting overlapping terrain.
- Correct nearby collision.
- Existing valid terrain until its replacement is usable.

Determine the smallest dependency closure needed for a replacement. Do not casually remove safety checks or replace them with skirts hiding incorrect ownership.

Keep distant rings independently publishable where safe.

Avoid repeated uploads or staging destruction when a small camera movement changes only part of the plan.

## 4. MAKE TERRAIN DATA THE PRIMARY REUSABLE PRODUCT

Stop treating each render patch as an isolated request to regenerate the surrounding world.

Introduce a shared, bounded terrain-data cache containing immutable or safely versioned numerical pages.

Cache products should include:
- Canonical heights.
- Required material/biome controls.
- Water information.
- Local feature and cave-entrance metadata.
- Derivative data where useful.
- Filtered visual representations at different scales.

Separate three concepts:
- Data-page size.
- Render-patch size.
- Collision-region size.

Render patches can remain 16 m. Broader regional data can use larger pages, but generating the first nearby patch must not require completing a huge page.

Permit partial-page production or small critical subpages.

### Nearby sampling

A 48×48 m central region sampled every meter has:
- 49×49 unique grid positions.
- 51×51 positions with a one-sample border for normal calculations.

Use this as a reuse opportunity, not a requirement to generate the entire area as one monolithic job.

Share overlapping samples between neighboring patches. Derive normals from already available neighboring heights whenever appropriate.

Reuse canonical samples for ground collision instead of evaluating the same positions again.

### Cache requirements

Keys must include:
- World identity and generator version.
- Terrain-change revision.
- World-space page coordinates.
- Sampling level or spacing.
- Data-product type.

Handle negative coordinates and supported large coordinates consistently. Use exact lattice coordinates where possible instead of fragile floating-point equality tests.

Do not silently quantize genuine off-grid cave queries into an inaccurate cache.

Support:
- Bounded eviction.
- Resident near-page protection.
- Coalescing of identical in-flight requests.
- Cancellation that respects multiple consumers.
- Targeted invalidation.
- Optional persistent caching after the memory path is correct.

Do not share mutable sampler “last result” fields between workers. Capture results into owned typed data.

## 5. OPTIMIZE THE C# SAMPLING HOT PATH

C# migration alone is not enough.

Use ordinary .NET arrays, typed records/structs, and appropriate .NET collections inside numerical generation. Convert to Godot collections only at engine boundaries where required.

Priorities:

### Avoid repeated world evaluation
Separate height-only, material, water, and feature queries. A collision or derivative sample should not calculate visual payloads it does not need.

Cache regional descriptors such as island influence, biome regions, drainage networks, and feature locations when they are reusable.

Evaluate only relevant biome contributions. Preserve meaningful transition weights.

### Remove unnecessary allocations
Replace repeated temporary dictionaries, arrays, Variant conversions, LINQ allocations, and resource-property lookups inside tight loops where profiling supports it.

Use immutable settings snapshots and worker-owned scratch buffers.

### Remove serialization-based memory accounting
Do not call GD.VarToBytes merely to determine the size of newly built payloads.

Track array lengths and allocation sizes directly. Estimate container overhead conservatively.

### Improve eviction
Replace whole-cache clearing at capacity with bounded page or entry eviction.

Keep frequently reused nearby samples alive.

### Improve change tracking
Do not hash and copy every unchanged mesh during every publication.

Use explicit source, topology, boundary, material, and feature revisions to identify dirty products.

Do not reduce correctness by checking only vertex positions. Material-only changes, water, cave cuts, and collision updates must still invalidate their relevant products.

Preserve canonical terrain results. Distinguish exact caching optimizations from approximations that could change the landscape.

## 6. SPLIT ESSENTIAL TERRAIN FROM SUPPLEMENTARY WORK

Refactor the patch builder so its first usable result is small and bounded.

The critical path should resemble:

Acquire regional context
→ sample missing canonical ground data
→ derive necessary normals/material controls
→ prepare required collision and local boundary data
→ upload
→ publish locally.

Move nonessential work into independent follow-up jobs:
- Cosmetic biome structures.
- Detailed material masks.
- Decorative geometry.
- Additional surface effects.
- Distant water detail.
- Underground content outside immediate traversal needs.

Do not classify everything except the heightfield as optional.

A rock shelf, cave mouth, mound, or structure that changes traversable ground must have its gameplay-relevant geometry and collision ready before the player can use it.

Cosmetic refinements must not move the ground under players after publication.

Allow optional detail failures to be reported without making otherwise valid terrain disappear.

## 7. IMPLEMENT REUSABLE GPU-DISPLACED TERRAIN GRIDS

This is the main rendering optimization.

Do not reconstruct and upload complete vertex arrays for every ordinary terrain patch when a reusable grid plus height data can represent it.

Create reusable grid templates once.

Initial visual options per 16 m patch:
- 17×17 vertices for the simplest representation.
- 33×33 vertices for a more detailed visual grid.
- 65×65 vertices for higher-quality close rendering when worthwhile.

Use appropriate cheaper templates farther away.

The CPU can still produce canonical heights at approximately 1 m spacing where sufficient. The render grid samples those cached heights through a vertex shader.

This is actual displacement of EXISTING vertices. Do not claim that an ordinary Godot shader creates additional vertices.

### Required implementation details

- World-aligned height sampling.
- Texture/page borders to prevent edge contamination.
- Suitable height precision.
- Matching coordinate conventions between CPU and GPU.
- Correct normals after displacement.
- Correct displaced bounds for visibility culling.
- Correct shadows.
- Reusable topology compatible with 3:1 transitions.
- Appropriate handling of masked patches and cave openings.
- No dependence on GPU readback for ordinary collision.

Sharing a grid mesh does not mean forcing the whole world into one giant draw call. Preserve useful patch-level culling.

### Reconstruction versus invented detail

Interpolation cannot recover an absent cliff, narrow ridge, or cave entrance.

Begin with a reconstruction that can match the canonical collision triangles closely. If smoother reconstruction is added, bound and measure its deviation.

Do not accidentally use bilinear height reconstruction over a cell while assuming it exactly matches a differently triangulated collision surface.

Higher visual grid density may support:
- Smoother bounded reconstruction.
- Small cosmetic displacement.
- Better transition geometry.

It must not manufacture meter-scale terrain absent from collision.

Keep dedicated geometry for overhangs, cave mouths, and important non-heightfield structures.

Do not use fragment-only hole hiding as a substitute for correct cave collision and surface ownership.

## 8. RETAIN HIGH QUALITY THROUGH SCALE-SEPARATED DETAIL

Use three detail scales:

A. Canonical geometry:
Hills, valleys, ridges, coastlines, movement-relevant ground.

B. Additional real geometry:
Cliffs, shelves, cave entrances, important geological formations, and locally necessary refinement.

C. Surface shading:
Fine sand, soil grains, pores, cracks, small stones, and material irregularity.

Reuse the project’s existing licensed textures and biome material systems.

Maintain:
- Correct world texture scale.
- Natural material transitions.
- Directional geological detail.
- Non-repetitive color variation.
- Correct normal orientation.
- Realistic roughness and wetness.

Use normal maps for fine detail. Make expensive parallax optional and limited to locations and distances where it visibly helps.

Do not move the entire expensive biome generator into a per-pixel shader executed every frame.

Bake or generate expensive visual data when a page changes, then render it cheaply.

Small cosmetic displacement must remain within a documented gameplay tolerance. Near cave openings, sharp seams, and contact-critical surfaces, reduce or disable it where necessary.

Shaders cannot fix a genuinely broken silhouette. Refine geometry where needed.

## 9. FIX DISTANT FILTERING WITHOUT REPEATED EXPENSIVE QUERIES

Retain the nested scale progression:

16 m → 48 m → 144 m → 432 m → larger rings.

Preserve the existing correct handling of partial ownership and 3:1 boundaries.

Replace repeated on-demand filtering neighborhoods with reusable filtered pages or an equivalently cached hierarchy.

Calculate normals from the filtered data itself rather than repeatedly applying the full filter to new offset samples.

Avoid generating an entire high-resolution landscape just to build one distant page. Support direct bounded-cost coarse generation with validated error, or reuse appropriate existing pages.

Preserve:
- Mountain silhouettes.
- Major valleys and ridges.
- Large cliffs.
- Coastlines and islands.
- Important water boundaries.

Do not average material IDs or packed categorical controls as ordinary colors. Filter continuous weights separately and preserve categorical meaning.

Feature preservation must not reintroduce uncontrolled high-frequency spikes.

Use an error criterion to decide where coarse geometry needs refinement. Verify results against the canonical terrain and existing visual references.

Update only affected transition dependencies rather than restitching all unchanged terrain.

## 10. MAKE CAVE GENERATION INCREMENTAL AND LOCAL

The nearby surface must not depend on completing broad underground discovery.

Refactor cave work into separately scheduled products where the existing deterministic generation permits:

1. Local entrance and surface-intersection metadata.
2. Surface cuts and entrance collision.
3. Traversable entrance sections.
4. Nearby connected cave sections.
5. Distant cave regions, formations, and decoration.

Preserve deterministic topology and valid connections across region boundaries.

Do not simply shorten discovery ranges and change the world.

Investigate lazy evaluation of region nodes, connections, and exposure tests so only the dependencies needed for local entrances are solved first.

Cache completed region descriptions and reuse them across workers and consumers.

If current entrance decisions genuinely depend on broad network calculations, expose that dependency and refactor it explicitly. Do not pretend unknown cave locations are safely known to be solid ground.

Publish surface cuts and the corresponding entrance geometry/collision atomically.

Never allow:
- Players entering missing collision.
- A known entrance being temporarily sealed.
- Holes appearing beneath players.
- Unrelated cave work blocking distant or unrelated surface patches.

Measure local entrance readiness separately from complete cave-network readiness.

## 11. ADD PREDICTIVE PREFETCH AND BOUNDED JOBS

Keep the selected maximum-quality visible area centered on the active camera, with independent physics interests around players and other relevant actors.

Maintain a larger data/collision prefetch region, biased toward movement.

Use measured latency and velocity to choose lead distance:

prefetch distance ≈ speed × generation latency + safety margin.

When one row of the central 3×3 is replaced, reuse the remaining rows. Prepare the incoming row before the player reaches it.

Support:
- Movement-direction prediction.
- Conservative coverage behind the player for reversals.
- Camera/player separation.
- Teleport destinations.
- Bounded queues.
- Short, cooperatively cancellable tasks.
- Fair shared scheduling with caves.

Do not reserve excessive workers for distant work while nearby safety tasks wait.

Do not repeatedly cancel useful shared page work because one render patch became obsolete.

Give publication/preparation jobs their own scheduling consideration so a queue full of long sampling jobs cannot indefinitely delay already-ready terrain.

Avoid main-thread waits, Task.Result, or immediate GPU synchronization in the normal streaming path.

## 12. MAKE GPU COMPUTE OPTIONAL, NOT A REQUIREMENT

First implement and benchmark reusable grids with CPU-produced height pages.

Then prototype GPU generation of suitable visual products:
- Detail height pages.
- Normal pages.
- Filtered visual pages.
- Material-control maps.
- Regular batched procedural fields.

Keep generated data resident on the GPU when it is only needed for rendering.

Do not compute data on the GPU, synchronously download it, build a CPU mesh, and upload it again as the default pipeline.

Verify the actual Godot version and renderer capabilities.

The Compatibility path must remain functional. Compute acceleration may use a supported Forward+ or Mobile configuration where measured performance justifies it.

Do not silently change the whole project’s renderer to enable compute.

If RenderingDevice textures are used, verify that they are created through a renderer-compatible device and updated on the correct thread. Do not assume a texture from a separate local RenderingDevice is automatically usable by the scene renderer.

Budget compute against normal rendering. A busy integrated GPU may perform worse if terrain compute consumes its remaining capacity.

Benchmark complete frame time and readiness latency, not shader execution alone.

Retain CPU fallback when:
- Compute is unavailable.
- The selected renderer does not support it.
- GPU memory is constrained.
- Measurements favor CPU generation.
- A compute job fails.

A computer without a dedicated GPU may still have integrated graphics. A truly headless server must not require any terrain rendering or RenderingDevice access.
